# Keyloom parallel delivery
**Status:** Ready | **Owner:** harnex | **Updated:** 2026-11-06 23:24

Scheduling only, for the pure Swift stack. The approved plan and seven WP documents define deliverables, ownership, acceptance and risk reviews. `/Users/naim/Repos/keyloom` is the integration checkout on `feature/keyloom-mvp`. One CLI worker per independent WP, each in its own delegate worktree, started only once its shared dependencies have passed review and integrated.

- [ ] **Precondition:** the Swift-only state (conversion, `Feasibility/`, `Keyloom/AppIdentity.swift`, tests, project, plans) is uncommitted in the primary checkout; a924be4 still holds the Rust bootstrap. A worktree from a924be4 or HEAD would be wrong. Do not fan out until Naim authorizes an integration commit of that state (no history rewrite, no commit without authorization). Record that SHA as the integration SHA and as the red-check base; if no commit is authorized, WP2+ cannot start worktrees and red checks use the content-hashed export from the plan.
- [ ] Hand workers absolute read-only paths for plans, Snippet-App-Plan.md and Keyloom.html while they are untracked. Never rely on an untracked file appearing in a worktree.
- [ ] Paths: a worker edits only its WP's Owned files in its worktree. Primary-integration paths (Keyloom.xcodeproj, schemes, Build/, new-file and test-target registration) are edited only by the integration owner, serialized with WP1; workers request registration there. Keyloom/KeyloomApp.swift and all scene/command wiring belong to WP4 alone. WP2 alone owns shared store and model APIs. A missing shared operation returns to its owner with a test, integrates first, then dependents update to that SHA. Park any slice that needs unfinished interfaces.
- [ ] Each worker uses its own derived data, temporary database and fixture settings. Ship no fake implementation to unblock a consumer. Fast-forward completed slices onto the latest integration SHA, read the whole diff, run impacted tests after each integration; cross-WP failures go to the owning worker.
- [ ] Reviewers never edit production files or validate their own work. Re-run early reviews after contract changes. Record the merged SHA, the authoritative FULL Release suite, red checks against the Swift-only base, secret scan and native UI results before calling delivery complete.
